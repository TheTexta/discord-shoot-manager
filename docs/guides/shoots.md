# Shoot workspaces

The bot creates and manages private shoot chats. It does not manage unrelated ticket channels. See [setup](setup.md), [configuration](../reference/configuration.md), and the [permission reference](../reference/permissions.md).

To enable shoots, create one ordinary text channel for invitations, one category for active shoots, and one category for archived shoots. Create a separate production-access role with no server-wide permissions, below the bot. Set these IDs in `.env.local` or the deployment environment (legacy `TVM_*` aliases also work):

```dotenv
SHOOT_ANNOUNCEMENT_CHANNEL_ID=
SHOOT_CATEGORY_ID=
SHOOT_ARCHIVE_CATEGORY_ID=
PRODUCTION_ACCESS_ROLE_ID=
```

Leave all three channel/category IDs unset to keep shoots disabled. Partial configuration is rejected; enabled shoots require the production-access role ID. The announcement channel should be readable by eligible members and allow them to add reactions. Deleting an invitation stops reaction joining for that shoot; existing participants keep access.

Give the bot View Channels, Read Message History, Send Messages, Embed Links, Add Reactions, and Manage Messages in the invitation channel. In both categories it needs View Channels, Read Message History, Send Messages, Send Messages in Threads, Add Reactions, Embed Links, Attach Files, Manage Channels, Manage Permissions (Manage Roles), and **Pin Messages**. Run `npm run discord:check` and restart/redeploy to register `/shoot`. No new privileged intent or Message Content Intent is needed.

Management commands and shoot form submissions allow the configured bot-administrator role (`BOT_ADMIN_ROLE_ID`, called **Admin Team** at TVM) or Discord **Administrator** permission. Role membership is checked by ID, not display name, on every interaction. Command defaults allow role-based access; the bot rejects unauthorized users privately. The shoot creator becomes the organizer and retains access. Membership verification is optional; shoot-only deployments must explicitly configure `SHOOT_ELIGIBLE_ROLE_IDS`.

| Command                  | Purpose                                                                                                                                                                           |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/shoot setup [members]` | Run in any server text channel. Optionally @mention up to 70 members, then enter the shoot name, local call time, and location. Creates a new private chat and shared invitation. |
| `/shoot edit`            | Update the details and joining window; updates the pinned brief and invitation.                                                                                                   |
| `/shoot crew`            | Privately show directly invited and reaction-joined participants.                                                                                                                 |
| `/shoot add user`        | Add an eligible member to an open shoot, including after reaction joining expires.                                                                                                |
| `/shoot remove user`     | Remove a participant from an open or archived shoot. The organizer is protected; eligible members can react again to rejoin while joining is open.                                |
| `/shoot close`           | Move the chat to the archive category, preserve participant reading access, and disable posting and new joins.                                                                    |
| `/shoot reopen`          | Return the chat to the active category and restore eligible members' access.                                                                                                      |

The setup/edit form has separate optional date (`YYYY-MM-DD`) and time (`HH:mm`) fields in `SHOOT_TIMEZONE`, defaulting to `America/Toronto`. Parsing and edit display use the same zone. A date with a blank time uses **12:00 pm (noon)**. A blank date makes the shoot **Unscheduled**; the time is ignored. Discord displays scheduled call times in each viewer's local timezone. Invalid dates, daylight-saving gaps, and repeated daylight-saving times are rejected. Changing the deployment timezone does not reinterpret saved timestamps. Setup/edit commands immediately acknowledge the request, prepare the form, and show a private **Open form** button. Buttons are bound to the requesting admin and channel, and expire after 30 minutes or a restart. Permission is rechecked on the button and modal submission. Setup drafts expire after 30 minutes; stale edit forms must be reopened.

The reaction joining dropdown offers **1 day** (default), **2 days**, **Week** (7 days), **Month** (30 days), and **Never**. The window starts when the shared invitation is first published and is independent of the call time. After expiry, the shoot stays open and existing members keep access; new members require an admin to use `/shoot add user`. Members can still remove their reaction to leave. Joining is blocked at the deadline; the invitation displays its expired state on the next synchronization (within about a minute). Changing the period through `/shoot edit` recalculates the deadline from the original publication time. Reopening does not reset it. Existing shoots created before this feature keep unlimited joining until an admin edits their window.

Directly invited members join immediately. Their display names appear only in the pinned shoot-channel brief; announcements do not list or ping them. Admins can add direct invitations with `/shoot add user` and remove either invited or reaction-joined participants with `/shoot remove user`. Removal clears both the direct invitation and the member’s 🎬 reactions, updates the private brief and crew list, and removes participant access. It works in open and archived chats, including for members who have lost eligibility. Removing an absent participant again is harmless. The organizer is protected; production-access holders and Discord administrators retain their role-based chat access even when removed from the crew. Bot-admin authority alone does not retain access after removal. Removed members can react again while joining is open, subject to eligibility and capacity, or an admin can re-add them to an open shoot. Reaction rejoining does not restore their former direct invitation. If reaction cleanup fails, stored participation is unchanged; if later channel synchronization fails, reconciliation retries the removal.

Other eligible members react **🎬** on the shared invitation to join, and remove it to leave. Reacting is membership in the chat, not attendance confirmation. Bots cannot join. Eligibility requires a configured eligible role or Discord Administrator permission, not an email verification record. With membership enabled, the default eligible roles are Member, Exec, and Bot Admin; an explicit `SHOOT_ELIGIBLE_ROLE_IDS` replaces that default. Shoot-only deployments must set that list. Roles are checked by ID, not name or position, for invitations, additions, reactions, and synchronization. Members losing all qualifying access lose participant grants on synchronization; the organizer retains access.

The bot uses explicit channel overwrites, not copied category permissions. Ordinary participants can read archives but cannot post; production-access holders and participating bot administrators retain posting. Management authority does not confer blanket visibility. Production access is assigned/removed manually, never through roster uploads, and does not confer management authority or ordinary eligibility. See the authoritative [permission matrix](../reference/permissions.md) and [TVM production-channel policy](../deployments/tvm.md#production-access). Participant-created threads are disabled. A maximum of 98 currently eligible participants includes the organizer; inactive historical invitations do not occupy seats. Reaction bursts coalesce over 250 ms with a trailing pass when dirty.

Shoot state survives restarts in the configured database (`tvm.db` by default). The bot reconciles on startup, reconnect, role/access changes and member departures, after enabled roster synchronization, and every minute, retrying interrupted operations. Recovery markers in channel topics and message footers identify resources whose Discord response was lost; keep them intact. Deleted pinned briefs are recreated. Routine synchronization/reactions do not recreate deleted announcements. Edit, reopening, or startup may republish without pinging or resetting the original joining deadline. Closed announcements are deleted 24 hours after closing, on the next pass; interrupted deletions retry. For older closed shoots, the announcement's last edit time is the fallback close time. Due cleanup stays final through edits/restarts; reopening can republish. Existing participants keep access while an announcement is gone, and admins can still add people to an open chat. A deleted shoot channel is marked missing and reported, never automatically recreated. See [persistence and recovery](../architecture/persistence-and-recovery.md).

Synchronization failures are logged immediately with the shoot, failed operation, safe Discord request metadata, source frames, and an incident reference. Temporary background Discord/network failures receive a two-minute grace period before an admin alert; rapid reaction events do not shorten it. Permissions and unexpected operational errors alert immediately. Each incident sends one alert, followed by one recovery notice after that workflow succeeds. Cosmetic reaction cleanup is tracked independently, so a successful permission update does not falsely resolve it. Failed alert deliveries retry on the next relevant pass. Incident history is in memory: restarts reset the grace period and cannot send recovery notices for earlier alerts. The normal one-minute reconciliation and five-minute health threshold are unchanged.

Invalid input and expired forms receive private feedback, not admin alerts. Operational command failures include an incident reference and distinguish changes awaiting synchronization from an action that was not queued, or a completed action whose confirmation failed. Do not repeat setup when the bot confirms that changes were saved.

This release includes no reminders, attendance tracking, production responsibilities, links, or shoot list command. Before enabling on a production server, verify with an admin and test members that outsiders cannot see chats, reaction joins/leaves work, direct invitations retain access, and closing produces a readable archive with ordinary posting disabled.
